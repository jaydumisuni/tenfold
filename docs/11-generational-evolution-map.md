# Tenfold Generational Evolution Map

**Status:** CANONICAL RECOVERY / EVOLUTION MAP  
**Authority:** TF-00 + frozen G2-00 for currently authorised behaviour  
**Important:** this document explains the intended generational system. It does **not** activate Gen 2.1, Gen 2.2, or any future generation by itself.

This document exists so a zero-context chat, agent, reviewer, or future Tenfold runtime can recover the complete evolution model rather than seeing only the Gen-1 → Gen-2 bootstrap.

---

## 1. The complete loop

Tenfold is intended to improve the **system that uses intelligence**, not to depend on making the underlying model larger.

The full long-term loop is:

```text
APPROVED PROJECTS
      ↓
CURRENT QUALIFIED TENFOLD
      ↓
execution campaigns
      ↓
measured outcomes / evidence
      ↓
what worked better?
      ↓
method observations
      ↓
evidence-backed method qualification
      ↓
proven execution improvements
      ↓
CURRENT TENFOLD executes later projects better
      ↓
more measured campaigns
      ↺
```

When a separately approved next-generation authority exists:

```text
CURRENT QUALIFIED TENFOLD
      ↓
uses the approved next-generation roadmap
      ↓
builds the successor generation
      ↓
successor runs in shadow / hybrid
      ↓
authority migrates only after proof
      ↓
successor proves self-construction capability
      ↓
successor may finish its already-approved roadmap
      ↓
clean repository-only qualification
      ↓
successor may become preferred runtime
```

The generational pattern therefore is:

```text
BUILD
  ↓
OPERATE
  ↓
MEASURE
  ↓
IMPROVE EXECUTION METHODS
  ↓
QUALIFY IMPROVEMENTS
  ↓
OPERATE BETTER
  ↓
BUILD NEXT APPROVED GENERATION BETTER
  ↺
```

The loop improves organisational execution without granting learned methods architecture authority.

## 6. Gen 2.1 — scale / incrementality — RESERVED, NOT AUTHORISED YET

Gen 2.1 is the intended future layer for making the already-proven Gen-2 constitution faster and more scalable.

Frozen G2-00 explicitly excludes/reserves from Gen-2.0 activation these Gen-2.1-class capabilities:

```text
Work Cells optimisation
Execution Forest optimisation
capability-cover optimisation
evidence reuse
minimal re-prove optimisation
advanced resource optimisation
```

Additional ideas discussed during design are **NON-AUTHORITATIVE CANDIDATE CONCEPTS** unless and until a separate future authority approves them:

```text
conflict trees
logical / physical worker multiplexing
incremental frontier optimisation
targeted proof invalidation
```

Purpose:

> **Do the same constitutionally valid work with less duplicated labour, less re-proof, better parallelism, and higher throughput.**

Gen 2.1 must not weaken G2-00 to gain speed.

A separate approved authority/roadmap is required before any Gen-2.1 capability becomes active. Candidate concepts listed here are recovery/design context only; they are not frozen scope.


The intended explanatory learning loop is:

```text
CAMPAIGN EXPERIENCE
        ↓
normalised observations
        ↓
METHOD CANDIDATE
        ↓
shadow / controlled experiment
        ↓
multiple campaigns / holdouts / transfer trials
        ↓
measured improvement?
        │
   no ──┴── reject / retain observation only
        │ yes
        ↓
independent qualification / assurance
        ↓
PROVEN METHOD
        ↓
Method Registry
        ↓
future campaigns may select it
within project + constitutional authority
```

This loop is design intent only until a separate Gen-2.2 authority defines and approves its exact mechanisms.

Promotion would require evidence such as, depending on future method class:

```text
less rework
fewer failures
faster time-to-proven
faster time-to-first-disproof
better throughput
lower resource cost
better recovery behaviour
better transfer across project classes
```

A method is never promoted merely because:

```text
"the AI thinks this is better"
```

The intended shape is:

```text
we tried it
→ measured it
→ challenged it
→ saw repeatable improvement
→ preserved constitutional safety
→ then promoted it under separately approved authority
```

## 9. Institutional improvement without model growth

Tenfold's long-term advantage is intended to come from retained organisational evidence.

Example:

```text
Project A
  ↓
method X performs badly
method Y performs better
  ↓
record evidence

Project B
  ↓
method Y works again
  ↓
stronger evidence

Project C / holdout
  ↓
method Y transfers successfully
  ↓
qualified Method Y

Future Project
  ↓
Tenfold already knows Method Y is appropriate
  ↓
less rediscovery
less rework
faster safe execution
```

The underlying model can be unchanged while the **system using the model** becomes more effective because prior proven execution knowledge is reusable.

That is institutional improvement, not unconstrained self-modification.

## 10. What learning is never allowed to become

Standing constitutional rule:

```text
learned method != project authority
```

Also:

```text
method evidence != architecture authority
successful optimisation != permission to weaken proof
higher throughput != permission to bypass assurance
historical success != permission to guess on a new project
```

A learned method may influence **how** already-approved work is executed only under the separately approved authority that enables that method system.

It may not decide:

```text
what the project should become
what requirements exist
which assurance is mandatory
whether uncertainty can be ignored
whether an unproven obligation is complete
whether TF-00 / G2-00 can be weakened
```

## 11. Building the next generation

The recursive generational rule is:

> **The current qualified Tenfold may build a separately approved successor generation using that successor's frozen authority and roadmap.**

The successor does not invent its own authority.

Generic future pattern:

```text
CURRENT QUALIFIED TENFOLD Gn
        ↓
OWNER / EXTERNAL AUTHORITY APPROVES G(n+1)-00
        ↓
freezes successor roadmap
        ↓
Gn constructs G(n+1)
        ↓
G(n+1) shadow / hybrid
        ↓
authority slices migrate only after proof
        ↓
G(n+1) proves self-construction minimum
        ↓
G(n+1) may finish its already-approved roadmap
        ↓
clean repository-only qualification
        ↓
G(n+1) preferred runtime if approved
```

If a future institutional-learning generation has already produced qualified execution methods, the current Tenfold may use those methods while building the successor **only within the method authority allowed by the then-current constitution**.

The methods can make construction faster/better. They cannot redefine the successor architecture.

## 12. Why self-construction and self-improvement are different

These concepts must not be conflated.

### Self-construction

```text
approved roadmap already exists
        ↓
Tenfold executes that roadmap against its own codebase
```

G2-27/G2-28 are this class.

### Institutional self-improvement

```text
measured campaign experience
        ↓
evidence-backed method candidate
        ↓
qualification
        ↓
future execution uses proven better method
```

This belongs to later separately approved institutional-learning authority such as the intended Gen-2.2 class.

### Architecture evolution

```text
external / Owner architecture authority
        ↓
new frozen generation authority + roadmap
        ↓
current qualified Tenfold builds it
```

Tenfold does not autonomously promote method learning into architecture evolution.
